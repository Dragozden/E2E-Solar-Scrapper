# Incident: Gold viewer permissions and ambiguous catalog pagination (15 Nov 2026)

Two *independent* failures appeared after the system grew from scraper/dbt into Docker/Streamlit/Airflow.

**Dashboard:** SQLSTATE `42501` / `InsufficientPrivilege` on `gold.current_panel_ranking`. The application successfully authenticated as the restricted `solar_dashboard` role but had insufficient `SELECT` privileges on a dbt Gold view. Model materialization may drop/recreate views; the original reader-setup was a one-time GRANT. Remediation: re-grant current object privileges and set **per-owner, per-schema default privileges** for new views in Gold. Confirm via a new read-only connection **after** a subsequent dbt rebuild. No elevated access is granted to `solar_dashboard`.

**Scraper:** The first catalog page parsed 24 out of 24 products and then stopped at the strict `count() != 1` check on the accessible name "Następne produkty". That check conflated duplicate presentation elements and differing destinations. Remediation: normalize every matching link's `href`, accept multiple controls when they lead to the same URL, reject different URLs and off-site links, and preserve loop/deduplication/empty-page guards. The `scraper.pagination_probe` read-only diagnostic fetches page one and prints link URLs if the live markup differs from offline fixtures.

**Data safety:** A failed scraper run should remain `FAILED` in `bronze.scrape_runs`. Earlier successful snapshots, Gold data and the verified PostgreSQL backup must not be deleted or reconstructed to make the dashboard appear healthy.

**Remaining risk:** A new dbt model-creator role requires default-privilege setup again. Re-materialization behavior and a clean restore are best validated in integration tests. Responsive/JS DOM changes on the retailer remain external dependencies even when local fixtures pass.
